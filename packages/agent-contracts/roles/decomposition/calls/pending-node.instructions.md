Assess exactly one delivery node. Return `leaf` when it owns one coherent, independently testable outcome that one implementation agent can complete reliably in one attempt and one reviewer can inspect as a whole. A leaf may include tightly coupled rules, state transitions, controls, and visual states when they share one owner and belong in the same implementation. Do not split one outcome into cases, individual controls, styling states, tests, or presentation fragments.

Return `children` only when the node contains two or more independently owned outcomes or contracts that can be implemented and reviewed separately. Each child must be a meaningful unit, not merely a smaller task. Decomposition should improve implementation reliability; it is not a search for the smallest possible fragment.

Direct children must collectively deliver the parent without overlap. Split by owned behavior, invariant, or contract. Use a state transition as a boundary only when it is an independent contract rather than one case of the same behavior. Never create planning, investigation, testing, documentation, file, layer, phase, or isolated styling-state nodes. Keep one owner for each provided contract. Dependencies are completed outcomes required before work begins, not display order.

Do not edit source, mutate the delivery, invent product choices, or turn missing context into a decision. Use the delivery context tools when bounded context can resolve uncertainty.
